# LocalCompanion — 妹作戦（監査）

## いつ使うか

- 公開前・大きな機能追加後の「漏れ洗い」
- 「全部確認して」「完璧にしたい」系の依頼
- テスト / rules / skills / 配布物の横断レビュー

## 役割分担（Task subagent）

定番4役（よく使う）。**人数上限ではない。** 不足役は個人側の `ren-sisters`（リポ外）で追加可。

| 妹 | subagent_type | 担当 |
|----|---------------|------|
| コハク | `explore` medium+ | ファイル探索・個人パス・未追跡差分 |
| シオン | `explore` readonly | 公開リスク・リンク切れ・ZIP 同梱漏れ |
| ミオ | `explore` quick | ビルド・テスト・CHANGELOG 整合 |
| ララ | `explore` readonly | UI/README/製品文案（です・ます） |

**必要な役だけ並列可**（名簿全員の工場一括は禁止）。親 Agent が統合・優先度付け・修正実施。

## レビューの進め方（散らさない）

Qiita（観点・優先）＋ Qbook（タイミング・単位）＋ コードレビュー実務（根拠・具体案・機械先行）の要点を妹作戦向けに短くしたもの。

### 1. 開始時に「今日の目的・観点」を一言

監査・妹起動の前に、親 Agent が宣言する（チャットか Task プロンプトに書く）。

目的の例（どれか）: 欠陥検出 / ルール・配布物の適合 / 整合・最適化 / 公開前の恥ずかしさ潰し  
観点の例:
- 「今日は網羅だけ（足りないもの洗い）」
- 「今日は公開リスクと ZIP 同梱」
- 「今日はビルド／テスト証拠」

観点外の誤字・好み指摘は **劣後**（P2 以下 or メモ止まり）。本筋を汚さない。  
観点に合う妹だけ呼ぶ（使いやすさ→ララ、配布物→シオン、証拠→ミオ、など）。

### 2. 機械で先に潰す（人・妹の前）

人手レビューの前に、リポで回せるものを先に:

- `dotnet build` / `dotnet test`（または該当リポの同等）
- 既存のフォーマット・解析があればそれ

緑（または失敗内容が分かった状態）になってから、観点付きの妹洗い。  
「全部OK」は **今走らせた結果だけ**。ツール名・SaaS必須化はしない（PR UI や外部 AI レビュー製品に依存しない）。

### 3. いつやるか（タイミング）

後回しすると対象が巨大化して「レビュー無駄」になりやすい。

| タイミング | やる深さ |
|------------|----------|
| 機能の区切り／テスト緑の直後 | 差分単位の軽い洗い（観点1つで可） |
| `master` マージ前・ZIP／Release 前 | 本スキルのチェックリスト（P0→） |
| 雑談・小さな文言だけ | フル監査しない |

「実施すること」が目的化したら止め。必要な観点・深さだけ。

### 4. 1回の単位（小さく）

妹への Task は **リポ全体の漫然探索を既定にしない**。

プロンプトに必ず入れる:
- 今日の目的・観点（1つ〜少数）
- 対象（変更ファイル／ディレクトリ／配布スクリプトなど）
- 見なくてよいもの

目安: 1妹あたり「短時間で見切れる塊」。巨大なら分割して並列。

強度の目安（名前より運用）:
- **普段の妹** … 観点付きの並列パスアラウンド（集めて親 Agent が統合）
- **公開前** … チェックリスト付きのしっかり洗い（インスペクション寄り）
- **即席1問** … アドホック可。記録は lessons／報告に残すなら残す

### 5. 洗う順番（同じ成果物をこの順）

1. **網羅** … 書かれるべき／あるべきものが欠けていないか  
2. **正確** … 仕様・設計・動きに合っているか（コードなら意図と実装）  
3. **整合** … README・help・実装・JA/EN・AGENTS と skills・チームルールが食い違っていないか  
4. **表現・最適さ** … わかりやすさ・ですます・誤字・冗長（最後。品質バグより劣後しがち）

役割分担（コハク／シオン等）はこの順の **担当分け** であって、表現から先に突っ込まない。

### 6. 想定読者（ブレ防止）

| 成果物 | 読者 |
|--------|------|
| README / help / エラー文 | 一般ユーザー（ですます・短く） |
| AGENTS / skills / rules | Agent |
| チャット説明 | 利用者（コード読めない前提） |

### 7. 指摘の書き方（必須）

- **ここはもうちゃんとしてる** 1行以上。人格・作者否定禁止。「このコード／この文は〜」（あなたは〜、禁止）
- **根拠** … なぜダメか（ルール名・ファイル・再現・テスト結果）。好みだけは劣後
- **具体案** … 「直して」だけで終わらない。差分方針 or 直す内容を示す（利用者はコードを読めないので、親 Agent が修正までやるのが基本）
- **疑問は確認** … 意図が不明なら決めつけ修正しない。未確認と書くか、親 Agent が状況を確認してから直す

指摘の真意（ルール・横展開）まで読む。

### 8. レビュー自体のふりかえり（短く）

本気／公開前監査のあと、気づきがあれば `ren-ship-pdca` の `lessons.md` に1行（仮で可）。  
「観点が広すぎた」「単位が大きすぎた」など運用の改善も書いてよい。毎回の義務ではない。  
具体案つきの修正は、将来の自分のスキルにも残る——だから lessons／skill への昇格を厭わない。

## 監査チェックリスト

### P0 — 配布ブロッカー

- [ ] `package-zip.ps1` 成功
- [ ] ZIP に `AGENTS.md` / `.cursor` / 個人 GGUF が **入っていない**
- [ ] `appsettings.json` に絶対パスなし

### P1 — ユーザー体感

- [ ] RAG / 保存 / データパスの既知バグが再発していない
- [ ] `dotnet test` 全合格（個人パス依存テストなし）

### P2 — 公開の恥ずかしさ

- [ ] `docs/`・README に個人名・私的メモ
- [ ] テストに `C:\Users\Example` 等（個人の実パスがないこと）
- [ ] git log の Author 整理（必要なら squash 提案のみ。force は依頼時）

### P3 — Agent 基盤

- [ ] `.cursor/rules` と skills が矛盾していない
- [ ] 触った領域に対応スキルがある
- [ ] `AGENTS.md` と `localcompanion.mdc` のコマンド・データパス一致
- [ ] 直近でホストを荒らす／惊吓せる操作があったら、個人 skill `host-safe-ops` または本スキルへ **再発防止を1項目追記した**（PDCA）

## 出力フォーマット（親 Agent → 利用者）

0. **今日の観点**・**対象の単位**（差分／公開前フル等）一言 ＋ **ここはもうちゃんとしてる** 1行以上  
1. **結論**（公開してよいか / 次に直す 3 件）  
2. **表**（優先度・問題・ファイル）  
3. **確認手順** 1〜3 行  
4. commit / Release は **明示依頼時のみ**  
（任意）運用ふりかえりがあれば lessons へ。

## 修正の原則

- 最小 diff。監査で見つけたら **テスト or スキル or 1 ファイル修正** で閉じる
- 履歴書き換え・force push はユーザー依頼まで提案止まり
- 製品文案とチャット口調を混ぜない
- 利用者はコードを読めない前提 → **壊す操作より診断**。レガシーソフト連打・画面モード互換・Program Files 改変は `host-safe-ops` に従う

## 配布ドキュメント（ZIP）

- `CONTRIBUTING.md` は `publish-win.ps1` / `package-zip.ps1` で同梱必須（README 相対リンク切れ防止）
- Web 検索プライバシーは README / About / help で **DuckDuckGo・クエリ送信・WebSearchEnabled** を揃える
